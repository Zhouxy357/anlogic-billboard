## 1. 仿真是什么、为什么非做不可

* **仿真 = 让 Verilog 代码在电脑里"空跑"一遍**，不接开发板，几秒钟出结果。
* 它验证的是**逻辑对不对**（状态机跳对没、计数差一没、握手丢数没）。
* 本工程**每一个能单独跑的模块都配了 testbench**：19 个 testbench、**313 条自动检查**，
  从按键消抖一直覆盖到 SD 卡协议栈和 SDRAM 帧缓存。
* **代价对比**：仿真 5 秒 vs 上板发现问题再改再烧 30 分钟。
  所以手册里写"能省 90% 上板调试时间"。

> **仿真和综合是两回事**：
> * **仿真**（`run_iverilog.sh`）= 在电脑里跑逻辑，用的是 `sim\tb_*.v`；
> * **综合**（TD 里双击 Read Design）= 把代码变成真实电路，用的是 `src\` 下的文件。
> 两者都要做，顺序是先仿真、后综合。

## 2. 两套工具链对照（用哪套、区别是什么）

本工程配了**两套独立仿真器**，跑同一批 testbench。

| 脚本 | 用哪个仿真器 | 覆盖范围 | 需要装什么 | 推荐度 |
|---|---|---|---|---|
| **`run_iverilog.sh`** | IC Coder 自带的 iverilog 12.0 | **21 项**（2 项静态检查 + 19 个 tb，313 条断言）| **什么都不用装** | ★★★★★ 日常就用它 |
| `run_all.sh` | ModelSim SE-64 2020.4 | 早期 4 个 tb（历史脚本，未随新增 tb 扩充）| ModelSim 要在 PATH 里 | ★★★☆ 交叉验证用 |

**为什么要两套？** 两个仿真器对语法严格程度不同，
一套能过、另一套报错，说明代码里可能有"仿真器特有"的写法 ——
本工程实测**两套都全绿**，说明代码写法是干净通用的。

> 命令行里没有 `vsim` 就说明 ModelSim 没装/没进 PATH，那时只用 `run_iverilog.sh` 也行。

| 静态检查 | 做什么 |
|---|---|
| `top_elaborate` | 用 `ip_stubs.v` 里的官方 IP 空壳，检查**顶层连线**能不能全部对上（端口名、位宽）|

> 所以用空壳"占位"来验证**你写的连线是对的**。真实 IP 的行为只能上板验证。

### 4.1 两个"辅助模型"（不是被测对象，是给 tb 用的假器件）

| 文件 | 干什么 | 被谁用 |
|---|---|---|
| `sim/sd_card_model.v` | **假 SD 卡**：收命令、回 R1/R7、发 0xFE+512 字节、回写响应 0x05；还故意让前 3 次 ACMD41 回"忙"，逼出上层的重试分支 | `tb_sd_card.v` |
| `tb_frame_rw.v` 里的 `sdr_beh` | **行为级 SDRAM**：`App_wr_en` 时写进去并记录地址，`App_rd_en` 后延迟 4 拍吐出数据 | `tb_frame_rw.v` |

> 这两个是"**假器件**"，只为让协议栈能被真正验一遍。它们**不属于设计代码**，
> 不加进 TD 工程；真实 SD 卡 / SDRAM 的行为仍必须上板验证。

### 4.2 编译告警的放行机制（`run_iverilog.sh` 的 `wallow`）

`run_iverilog.sh` 里的 TESTS 表可以带第 4 段（分号分隔的"已知无害告警"指纹）。
目前只有 `tb_frame_rw` 用到，放行 4 条：

| 告警 | 为什么无害 |
|---|---|
| `dangling input port 14 (dib) floating` | 安路 IP Generator 生成的 FIFO 内部把未用的写端口悬空，**厂商自己的代码**，改了就不是"原样"了 |
| `Port 20 (rdusedw) of frame_fifo_write expects 10 bits, got 9`（+ `Padding 1 high bits`，共 3 条）| **官方 support 代码本身**的位宽不一致：`frame_fifo_write` 声明 `input[9:0] rdusedw` 而连线是 9 位。高位被补 0，而 FIFO 实际用量远小于 512，行为无影响 |

**清单之外的任何告警仍然判失败** —— 这样既能让官方代码保持原样，又不会把新引入的隐患放过去。

## 5. 结果怎么读 —— 什么样才算"正确"

### 5.1 判定标准（三条，必须同时满足）

| # | 看什么 | ✅ 正确 | ❌ 不正确 |
|---|---|---|---|
| ① | **汇总行**（倒数几行）| `通过 21 项，失败 0 项` | 出现 `失败 N 项`（N > 0）|
| ② | **每一项的结论** | 20 行**全带 `PASS`** | 任何一行带 `FAIL` |
| ③ | **括号里的计数** | `n/n` 两边相等（如 `18/18`）| 如 `17/18` = 挂了 1 条 |

> **只满足一条不行，要三条全中。** 反过来，只要 ① 是 `失败 0 项`，
> ②③ 就必然满足 —— 所以**图快就只看 ① 那一行**。

### 5.4 反面：出现这些就是"不正确"

| 你看到的 | 含义 | 怎么办 |
|---|---|---|
| `### RESULT tb_xxx : FAIL (16/18) ###` | 逻辑真有错，挂了 2 条断言 | 找下面 `### FAIL idx=N ###` 定位；跑 `python check_results.py` 看中文 |
| `通过 19 项，失败 1 项` | 有一整套挂了 | 往上翻那一套的输出定位 |
| `有清单外告警` | 出现了没登记过的编译告警 | 看它打印的告警内容；确认无害就把它加进 TESTS 表第 4 段 |
| `Unknown module type: xxx` | **编译就失败**，不是逻辑问题 | 文件没点名 / 模块名拼错 |
| `$readmemh: cannot open file` | 不在 `sim` 目录下跑 | `cd /c/FPGA/billboard_prj/sim` 再跑 |
| 输出停在某一节不动 | 仿真卡死（tb 里等待条件永不满足）| 多半是改坏了 tb |
| 中文显示成 `閫氳繃锛�` | ⚠️ **不算错！** 只是终端编码问题 | 只看 ASCII 的 `PASS` / `FAIL` / 数字 |

   波形里能看到**按键抖动被吃掉、输出只跳一次** —— 这才叫眼见为实。

### 5.7 ⚠️ 最重要的一句：仿真"正确" ≠ 上板"正确"

**仿真全绿只证明"可以上板了"，不证明"上板一定对"。**
原因：PLL、SDRAM、HDMI PHY、SD 卡底层是**官方加密 IP**，iverilog 里要么用 `ip_stubs.v` 的**空壳**，
要么用了我们自己写的**行为级模型**（`sd_card_model.v` / `sdr_beh`）；
真芯片里的行为只有上板才能验证：

| 仿真里替代的 | 真实器件 | 仿真覆盖不到的 |
|---|---|---|
| `ip_stubs.v` 空壳 | PLL / SDRAM 控制器 / HDMI 收发器 | 时钟频率、锁定时间、真实时序余量 |
| `sd_card_model.v`（假卡）| 真实 TF 卡 | 卡的上电延时、真实繁忙时长、兼容性 |
| `sdr_beh`（行为级 SDRAM，固定 4 拍延迟）| 真实 SDRAM 控制器 | 真实读延迟、Sdr_busy 仲裁、自刷新抢占 |

> 特别是 `frame_fifo_read` 里有一句 `rd_burst_finish = (rd_vld && rd_delay == 10)`，
> 它**假定一次突发读的数据在 10 拍内全部回来**。仿真里我们的模型延迟 4 拍，满足；
> 真芯片上如果延迟更长，这里就有风险 —— 上板必须重点看这一段（现象：画面撕裂/错行）。

上板后真出问题 → 用 TD 自带的 **ChipWatcher**（`Tools → Debug Tools → ChipWatcher`）抓真实信号，
详见主手册**第 6 节**。

## 6. 跑不过怎么办（按顺序排查）

1. **确认你在 `sim` 目录下跑的** —— tb 里的 `$readmemh("audio_rom.hex")` 是相对路径，
   必须在 `sim\` 目录里执行，否则找不到素材文件。
   ```bash
   cd /c/FPGA/billboard_prj/sim && pwd    # 应输出 .../billboard_prj/sim
   ```
2. **看是"编译失败"还是"断言失败"**：
   * 编译失败 → 通常是文件没点名 / 模块名拼错 / 语法问题；
   * 断言失败 → 逻辑真的不对（`### FAIL idx=N ###` 指出第几项）。
3. **用 `python check_results.py` 看中文**，定位到具体哪一条断言。
4. **只跑那一个模块**：`bash run_iverilog.sh key`（换成挂掉的那个）。
5. **想看内部信号值** → 路线 C 看波形，或临时加 `$display` 打印。

## 7. 常见报错对症表

| 报错 | 原因 | 怎么修 |
|---|---|---|
| `Unknown module type: xxx` | 编译时**没点名**那个 `.v` 文件 | 在命令行里补上该文件；或看 `run_iverilog.sh` 里的文件清单 |
| `$readmemh: cannot open file` | 不在 `sim` 目录下跑 | `cd /c/FPGA/billboard_prj/sim` 再跑 |
| `syntax error: malformed statement` | `begin : label` 块里声明了 `reg`（iverilog 不允许）| 把变量提到模块级（本工程已规避） |
| 中文显示成 `閫氳繃锛�` 之类的乱码 | 中文经**位向量参数**传给 tb 时字节被改写 | **不影响判断**，只看 ASCII 的 `### RESULT ... PASS/FAIL ###` 行 |
| `#1000` 之类的整点延时导致结果飘 | 延时正好落在时钟沿上，与时钟块竞争 | 改成落在两个沿中间（如 `#1002`）。本工程 `tb_startup_pulse` 踩过 |
| ModelSim `vopt-7063` | `$readmemh` 的文件名写成 parameter 了 | 文件名只能写字面量（本工程已规避） |
| ModelSim 一个 `.do` 里串多个 tb，第二个跑不到 | `vsim -c` 下 `$finish` 会结束整个会话 | 分开跑，或改用 `run_all.sh` |
| `vlog: command not found` | ModelSim 没进 PATH | 只用 `run_iverilog.sh` 即可（免安装） |
| `vlib work` 报 `Library already exists at "work"` | work 库以前建过 | **无害，继续往下走** |
| `cd` 报 `No such file or directory` / `vlog` 报 `ENOENT`（但文件明明在） | 命令是手敲的：`cd` 后少空格、混入全角字符 | 从手册**复制粘贴**，路径用 Tab 补全 |
| `vlog` 显示 `0 Errors`，`vsim` 却仍报 `Error loading design`（左下 `No Design Loaded`） | ModelSim 优化缓存 / GUI 加载的**暂态故障**，代码和库都是好的 | 在 Transcript 的 `ModelSim>` 后**再敲一次** `vsim tb_xxx`；还不行就关掉 ModelSim，删掉 `sim\work\` 从 `vlib work` 重新来 |
| `add wave -r /*` 报 `(vish-4014) No objects found matching '/*'`，Wave 窗口空白 | `vsim` 没带 `-voptargs=+acc`，加载的是优化版设计，信号被藏掉 | Transcript 敲 `quit -sim`，再用 `vsim -gui -voptargs=+acc tb_xxx` 重新加载 |
| Git Bash 里敲 `add wave -r /*` 报 `bash: add: command not found`；敲 `run -all` 蹦出 `Tang Dynasty` 横幅 | 这两条是 **ModelSim Transcript** 的内部命令，不是 bash 命令；bash 敲 `run` 会误命中 TD 的 `run.exe` | 分清窗口：`vlib/vlog/vsim` 在 **Git Bash**，`add wave/run` 在 **ModelSim 下方 Transcript**（`VSIM n>`）。误触发的 TD run 按 Ctrl+C 停掉，无害 |

## 8. 什么时候必须重跑仿真

> **铁律：改了任何 `.v` 或 `sim/tb_*.v`，必须重跑仿真。**

推荐顺序（不许跳步）：

```
① cd /c/FPGA/billboard_prj/sim && bash run_iverilog.sh    ← 必须"失败 0 项"
② python tools/build_manual.py                            ← 手册与源码同步
③ TD 里 Read Design → Syn Opt                             ← 综合 0 ERROR
④ 上板（手册第 13 步清单）
```

**绝不"改完代码直接烧板子"** —— 那样出了问题你连是哪一级的毛病都分不清。
